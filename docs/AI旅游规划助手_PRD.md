# AI 旅游规划助手产品需求文档（PRD）

> 文档版本：V0.1  
> 产品阶段：MVP 规划  
> 更新日期：2026-09-27  
> 目标平台：Web 优先，后续扩展至移动端  
> 核心场景：单城市 2–5 日自由行规划

---

## 1. 文档概述

### 1.1 产品名称

暂定名称：AI 旅游规划助手。

### 1.2 产品定位

AI 旅游规划助手是一款面向自由行用户的智能行程规划工具。用户提供目的地、旅行日期或天数、预算、同行人和兴趣偏好后，系统通过大模型与地图、天气、地点信息等工具协同，生成路线合理、时间可执行、预算可解释，并可持续修改的逐日行程。

产品不以生成泛化旅游攻略为主要目标，而是帮助用户完成从模糊旅行意向到可落地行程安排的决策过程。

### 1.3 文档目的

本文档用于明确 MVP 的产品目标、功能范围、核心流程、业务规则、数据结构、非功能要求、验收标准及后续迭代方向，为产品设计、技术方案、交互设计和研发拆解提供依据。

## 2. 背景与问题

### 2.1 用户现状

自由行用户通常需要在内容平台、地图、天气、票务和酒店平台之间反复切换，手动完成以下工作：

- 搜索值得前往的景点、餐厅和活动。
- 判断地点是否符合个人兴趣和同行人需求。
- 核对营业时间、预约要求和预计停留时间。
- 计算景点之间的距离与交通耗时。
- 将候选地点分配到不同日期并安排访问顺序。
- 控制门票、餐饮、市内交通等费用。
- 在天气、闭馆、迟到或临时改变偏好后重新规划。

这一过程耗时较长，且容易产生路线绕行、时间冲突、行程过密和预算失控等问题。

### 2.2 现有 AI 方案的主要问题

- 行程内容看似完整，但地点、营业状态或交通信息不准确。
- 依赖模型常识直接生成，缺少地图和实时信息核验。
- 只输出自然语言，无法稳定执行或继续编辑。
- 未充分考虑抵达时间、闭馆时间、预约时段和交通缓冲。
- 修改一个项目后往往重写全部行程，破坏用户已确认的安排。
- 预算来源不透明，估算结果缺少置信度。

### 2.3 产品机会

将大模型的偏好理解和解释能力，与地图工具的真实地点及路线数据、程序化约束校验能力结合，形成一个可生成、可验证、可调整的旅行计划系统。

## 3. 产品目标

### 3.1 MVP 目标

针对单城市 2–5 日自由行，用户在 5 分钟内完成需求输入并获得一份满足以下条件的行程：

- 地点真实且可定位。
- 每日路线基本顺路。
- 时间安排不存在明显冲突。
- 包含景点间交通方式和预计耗时。
- 提供可解释的费用估算。
- 支持删除、替换、锁定和局部重新规划。

### 3.2 用户价值

- 降低行程规划的信息搜集和计算成本。
- 提高行程的真实性、合理性和可执行性。
- 允许用户通过自然语言低成本地持续调整计划。
- 在旅行途中出现变化时快速获得替代方案。

### 3.3 商业目标

MVP 阶段优先验证用户需求和留存，不以交易收入为首要目标。后续可通过酒店、门票、交通、当地活动和会员订阅实现商业化。

### 3.4 非目标

MVP 暂不包含：

- 多城市、跨国或复杂跨城交通规划。
- 机票、火车票、酒店的实时价格比较与直接预订。
- 签证、保险及复杂入境政策服务。
- 完整旅行社区、游记内容平台。
- 团队或企业差旅审批。
- 完全自动替用户完成付费交易。

## 4. 目标用户与使用场景

### 4.1 核心用户

#### 用户 A：没有时间做攻略的自由行用户

- 对目的地有基本意向，但不熟悉当地情况。
- 希望快速获得一份可以直接执行的行程。
- 愿意回答少量问题，不愿填写复杂表单。

#### 用户 B：已有部分计划的半自助用户

- 已确定酒店或少数必去地点。
- 需要系统补全剩余时间，并优化访问顺序。
- 希望保留自己已经确定的安排。

#### 用户 C：旅行中的临时调整用户

- 因天气、闭馆、迟到、体力或兴趣变化需要修改计划。
- 希望仅调整受影响部分，而不是重新生成全部行程。

### 4.2 典型场景

1. 用户计划国庆到成都旅行 4 天，预算 4000 元，偏好美食和人文，希望每天不要太累。
2. 用户已经预订北京某酒店，并确定第二天上午参观故宫，希望补全其余行程。
3. 用户在杭州旅行时遇到下雨，希望将当天下午改为室内活动。
4. 用户发现当天起晚两个小时，希望保留晚餐预约并压缩其他安排。
5. 用户认为行程预算过高，希望减少 1000 元但保留两个必去景点。

## 5. 产品原则

1. **真实性优先**：地点、坐标和路线信息应尽可能由外部工具核验，不依赖模型记忆。
2. **可执行优先**：必须考虑交通、营业时间、停留时间、用餐、休息和缓冲时间。
3. **用户可控**：用户可以锁定、替换或删除任一行程项。
4. **局部修改优先**：调整时尽量保留用户已确认内容，减少无关变更。
5. **解释而非伪精确**：明确区分确定信息、估算信息和待核验信息。
6. **先结构化后表达**：系统先生成并校验结构化行程，再渲染为自然语言和地图视图。

## 6. MVP 功能范围

### 6.1 功能优先级定义

- P0：缺失则无法形成完整 MVP。
- P1：显著提升体验，应在首个公开版本中实现。
- P2：可在验证核心需求后迭代。

### 6.2 功能清单

| 模块 | 功能 | 优先级 |
|---|---|---:|
| 需求收集 | 目的地、日期或天数、预算、同行人、偏好输入 | P0 |
| 需求收集 | 必去、排除、住宿位置、节奏与交通偏好 | P0 |
| 智能补问 | 自动识别关键信息缺口并发起少量追问 | P0 |
| 地点检索 | 通过地图工具搜索、核验并标准化 POI | P0 |
| 行程生成 | 生成按天、按时间排列的行程 | P0 |
| 路线计算 | 提供相邻地点间交通方式、距离和耗时 | P0 |
| 约束校验 | 检查时间、营业时间、路线和预算冲突 | P0 |
| 行程展示 | 时间轴、地图点位、每日摘要和预算展示 | P0 |
| 行程编辑 | 删除、替换、调整时间、拖动排序 | P1 |
| 状态控制 | 锁定行程项，重排时保持不变 | P1 |
| 局部重排 | 按单日、时间段或指定条件重新规划 | P1 |
| 方案选择 | 舒适、均衡、覆盖优先等方案 | P1 |
| 信息标识 | 展示数据来源、更新时间和核验状态 | P1 |
| 分享导出 | 分享链接、图片或日历导出 | P2 |
| 天气联动 | 根据天气推荐替代计划 | P2 |
| 多人协作 | 邀请同行人投票和合并偏好 | P2 |

## 7. 核心用户流程

### 7.1 新建行程

1. 用户点击“创建行程”。
2. 输入目的地、旅行日期或天数、预算等基本信息。
3. 系统通过自然语言对话或快捷选项收集偏好。
4. 系统识别缺失的硬约束，只追问对结果有明显影响的问题。
5. 用户确认需求摘要。
6. 系统检索候选地点，并计算路线和时间。
7. 系统生成结构化行程并执行约束校验。
8. 系统向用户展示默认推荐方案及备选方案。
9. 用户编辑、锁定或重新规划部分内容。
10. 用户保存、分享或在旅行中继续使用该行程。

### 7.2 局部重新规划

1. 用户提出修改请求，例如“第二天下午改成室内活动”。
2. 系统识别影响范围和必须保留的行程项。
3. 系统将锁定项、已预约项和用户指定保留项设为不可移动约束。
4. 系统重新搜索候选地点并计算受影响路线。
5. 系统仅替换受影响的时间段。
6. 系统说明修改内容、修改原因以及预算和时间变化。
7. 用户确认后更新正式行程；未确认前保留原版本。

### 7.3 异常处理

当工具调用失败或数据不足时：

- 保留已成功取得的数据，不重复执行无效查询。
- 明确标记未核验信息，不将推测描述为事实。
- 提供重试、手动选择地点或使用候选方案的入口。
- 在无法满足全部约束时，明确指出冲突并请用户选择取舍。

## 8. 详细功能需求

### 8.1 需求收集与偏好建模

#### 8.1.1 基础输入

系统应支持以下字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| 目的地城市 | 是 | MVP 仅支持单城市 |
| 开始日期 | 否 | 未确定日期时可仅输入天数 |
| 结束日期或天数 | 是 | 支持 2–5 日 |
| 抵达时间 | 否 | 未填写时使用默认可游玩时间 |
| 离开时间 | 否 | 用于约束最后一天行程 |
| 总预算 | 否 | 支持总预算或人均预算 |
| 同行人数 | 是 | 默认 1 人 |
| 同行人类型 | 否 | 成人、儿童、老人等 |
| 住宿地点 | 否 | 支持酒店名称、地址或区域 |
| 兴趣偏好 | 否 | 美食、历史、自然、购物、拍照等 |
| 行程节奏 | 否 | 轻松、均衡、紧凑 |
| 交通偏好 | 否 | 公交地铁、打车、自驾、步行 |
| 必去地点 | 否 | 不应在重排中自动删除 |
| 排除地点或活动 | 否 | 不进入候选集合 |
| 饮食及无障碍需求 | 否 | 过敏、素食、轮椅等 |

#### 8.1.2 智能补问规则

- 每轮最多询问 1–3 个问题。
- 只有当信息缺失会显著影响方案时才补问。
- 对非关键字段使用可见的默认值，允许用户稍后修改。
- 在生成前展示需求摘要，避免错误理解持续传播。
- 用户使用自然语言输入时，应将内容映射到结构化字段。

#### 8.1.3 验收标准

- 用户仅输入“上海三天，两个人，预算 5000，喜欢美食和建筑”时，系统可以形成结构化需求。
- 日期、预算口径或人数存在歧义时，系统能够识别并补问。
- 用户可以在生成前修改任一已识别条件。

### 8.2 地点搜索与核验

#### 8.2.1 功能要求

- 通过高德地图 MCP 或等价地图服务搜索 POI。
- 保存地图服务返回的唯一标识、名称、地址、坐标、分类等信息。
- 对同名地点进行消歧，优先选择目标城市及合理行政区内的结果。
- 对候选地点进行去重和基础质量过滤。
- 支持按关键词、类别、地理范围和用户偏好检索。
- 营业时间、票价、预约要求等无法确认时应标为待核验。

#### 8.2.2 候选地点评分

候选地点可按以下维度计算综合得分：

- 用户兴趣匹配度。
- 与必去地点及住宿地点的地理关系。
- 路线增加的额外时间。
- 预计停留时间与可用时间段的匹配度。
- 预算适配度。
- 同行人适配度。
- 数据完整度及可信度。

#### 8.2.3 验收标准

- 正式行程中的地点必须包含可用坐标或地图唯一标识。
- 不得将另一个城市的同名地点误加入行程。
- 工具无结果时，不得由模型虚构地址或坐标。

### 8.3 智能行程生成

#### 8.3.1 生成策略

1. 根据位置、兴趣和时间窗形成候选地点集合。
2. 对地点进行地理聚类，优先将邻近地点安排在同一天。
3. 优先放置固定时间、预约时段和必去地点。
4. 根据路线耗时安排其余地点的访问顺序。
5. 插入交通、用餐、休息和必要缓冲时间。
6. 计算每日强度、费用和总预算。
7. 执行冲突检查，不通过时自动调整。
8. 输出默认方案，并可选输出不同侧重点的备选方案。

#### 8.3.2 行程项类型

- 景点或活动。
- 餐饮。
- 交通。
- 休息或自由活动。
- 入住、退房、抵达和离开节点。
- 用户自定义项目。

#### 8.3.3 默认规划规则

- 默认每日正式活动不早于 09:00、不晚于 21:00，用户另有要求时除外。
- 连续活动之间必须包含实际交通时间。
- 每半天至少保留一段缓冲，或在总时间中加入合理缓冲比例。
- 不应为了增加景点数量而明显牺牲路线合理性。
- 第一天和最后一天应根据抵达、离开时间降低安排强度。
- 轻松、均衡、紧凑模式应影响每日地点数量、步行量和缓冲时间。
- 无法满足全部约束时，优先保留锁定项、已预约项和必去项。

#### 8.3.4 多方案输出

P1 阶段支持：

- 舒适优先：减少地点数量，增加休息和缓冲。
- 均衡推荐：平衡覆盖度、路线和体力。
- 覆盖优先：在合理范围内增加地点数量。

#### 8.3.5 验收标准

- 每个行程项包含开始时间、结束时间、预计停留时间和地点信息。
- 相邻地点之间包含交通方式及预计耗时。
- 行程中不存在明显时间重叠。
- 同一天不得出现不合理的远距离往返，除非用户指定。
- 生成失败时应返回可理解的冲突原因，而不是空白结果。

### 8.4 约束校验

#### 8.4.1 硬约束

硬约束不满足时不得直接发布为正式方案：

- 日期和时间不得重叠或倒序。
- 固定预约时间不得被移动。
- 锁定项目不得在未经用户确认时删除或更改。
- 地点必须位于目标城市或经用户明确确认的周边范围。
- 交通时间必须计入日程。
- 抵达前、离开后不得安排活动。

#### 8.4.2 软约束

软约束不满足时可生成方案，但应降低评分或提示用户：

- 每日步行量超过用户偏好。
- 总预算超出目标。
- 每日活动密度过高。
- 连续多日安排高体力活动。
- 用餐时间明显偏离常规时段。
- 某地点营业时间或预约信息未核验。

#### 8.4.3 校验输出

系统应返回：

- 校验状态：通过、带提醒通过、未通过。
- 问题类型和受影响行程项。
- 自动修复结果或建议用户做出的取舍。
- 修改前后的时间、费用和路线差异。

### 8.5 路线与交通

#### 8.5.1 功能要求

- 计算住宿地、景点、餐厅及交通枢纽之间的路线。
- 根据用户偏好选择步行、公交地铁、驾车或打车等方式。
- 展示距离、预计时间以及必要时的换乘摘要。
- 对同一路线结果进行缓存，减少重复工具调用。
- 路线不可用时，提供替代交通方式或提示人工确认。

#### 8.5.2 验收标准

- 每个非首个行程项均能说明如何从上一地点到达。
- 交通时间发生变化后，后续时间轴可以重新计算。
- 用户修改住宿地点后，可以触发行程路线重新评估。

### 8.6 预算管理

#### 8.6.1 预算分类

- 门票及活动。
- 餐饮。
- 市内交通。
- 住宿，可由用户输入或在 MVP 中作为固定值记录。
- 其他预留费用。

#### 8.6.2 费用状态

- 已确定：来自用户订单或可靠数据源。
- 估算：根据规则、区间或经验值计算。
- 待确认：缺少足够信息。

#### 8.6.3 功能要求

- 展示每日预算和全程预算。
- 标注费用口径：总价、人均、单次或区间。
- 预算超出时提示超出金额及主要成本来源。
- 支持“保持必去项，将预算降低 X 元”等自然语言修改。

#### 8.6.4 验收标准

- 总预算应能追溯到各预算分类和行程项。
- 不得将估算费用展示为确定价格。
- 删除或替换收费项目后，总预算应同步更新。

### 8.7 行程展示与编辑

#### 8.7.1 页面结构

- 顶部：目的地、日期、人数、预算和方案状态。
- 左侧或主区域：按天排列的时间轴。
- 地图区域：当前日点位、路线和顺序。
- 摘要区域：每日强度、步行量、交通时间和预算。
- 对话入口：通过自然语言调整行程。

#### 8.7.2 行程项操作

- 查看详情。
- 锁定或解除锁定。
- 删除。
- 替换为附近或同类地点。
- 调整开始时间或停留时长。
- 拖动排序。
- 标记为已预约或已完成。

#### 8.7.3 状态定义

- 候选：尚未加入正式行程。
- 已规划：已进入正式方案，但未锁定。
- 已锁定：重新规划时默认保持不变。
- 已预约：具有固定时间或已产生订单。
- 已完成：旅行中已实际完成。
- 已取消：从当前方案中移除，但保留历史记录。

#### 8.7.4 验收标准

- 用户能够清楚识别哪些内容可调整、哪些已锁定。
- 删除行程项后，系统提示是否需要自动补充其他地点。
- 拖动或修改时间后，系统自动检查后续冲突。

### 8.8 局部重排与版本管理

#### 8.8.1 修改请求示例

- “第二天下午下雨，换成室内活动。”
- “保留晚餐，把上午开始时间改成 11 点。”
- “这个景点不去了，找一个附近适合儿童的地方。”
- “每天少走 5000 步。”
- “总预算降低 1000 元。”

#### 8.8.2 业务规则

- 修改前识别时间范围、地理范围和受影响约束。
- 默认不修改锁定、已预约和已完成项目。
- 正式覆盖前展示变更摘要。
- 保存最近版本，允许用户撤销本次调整。
- 说明被删除、替换、移动或新增的项目及原因。

#### 8.8.3 验收标准

- 用户只修改第二天下午时，第一天和第三天不应发生无关变化。
- 用户指定保留的项目不得被自动删除。
- 用户可以查看修改前后的关键差异并撤销修改。

## 9. 智能体与工具设计

### 9.1 推荐职责划分

| 组件 | 主要职责 |
|---|---|
| 对话与意图模块 | 理解用户需求、补问、解释结果 |
| 旅行需求解析器 | 将自然语言转换为结构化约束 |
| POI 检索模块 | 调用地图工具搜索并标准化地点 |
| 候选推荐模块 | 计算地点与用户偏好的匹配度 |
| 行程调度器 | 进行分日、排序、时间安排和缓冲插入 |
| 路线计算模块 | 获取地点之间的距离、方式和耗时 |
| 约束校验器 | 检查硬约束和软约束 |
| 预算模块 | 汇总、分类和解释费用 |
| 行程渲染模块 | 将结构化数据转换为时间轴、地图和文本 |
| 版本管理模块 | 保存修改记录、差异和撤销点 |

### 9.2 工具调用原则

- 模型决定“需要查询什么”，工具返回“真实数据是什么”。
- 工具结果必须经过字段校验和标准化后才能进入规划过程。
- 对相同地点和路线启用缓存，设置缓存有效期。
- 每次规划设置工具调用次数和总耗时上限。
- 工具返回的文本视为不可信外部数据，不得作为系统指令执行。
- 关键工具失败时允许降级，但必须向用户说明影响。

### 9.3 高德地图 MCP 能力需求

集成时至少需要验证或封装以下能力：

- 关键词或类别地点搜索。
- 地点详情查询。
- 地址与坐标转换。
- 步行、公交、驾车等路线规划。
- 距离和预计交通时间获取。
- 行政区或城市范围判断。

具体接口、字段、调用限制和商用许可应以实际接入时的官方文档与服务协议为准。

### 9.4 智能体执行流程

```text
解析用户输入
    ↓
形成结构化需求与约束
    ↓
检查关键信息是否缺失
    ↓
搜索并标准化候选 POI
    ↓
按地理位置和日期进行分组
    ↓
计算候选路线与交通耗时
    ↓
生成时间轴和预算
    ↓
执行硬约束、软约束校验
    ↓
不通过则调整并再次校验
    ↓
生成可编辑方案和解释
```

### 9.5 降级策略

- 地点搜索失败：提示用户换关键词或手动选择地图地点。
- 路线服务失败：保留地点建议，但不发布精确时间表。
- 营业时间缺失：标记为“出发前需确认”。
- 预算数据缺失：提供区间估算并注明依据不足。
- 多次调整仍无法满足约束：列出冲突条件，让用户选择放宽项。

## 11. 页面与交互需求

### 11.1 首页或创建页

首屏直接进入创建流程，不设置大篇幅营销介绍。主要元素：

- 目的地输入框。
- 日期或天数选择。
- 人数与预算输入。
- 偏好快捷标签。
- 自然语言补充输入框。
- “生成行程”主操作。

### 11.2 规划生成状态

系统可展示用户能理解的阶段状态：

- 正在理解旅行需求。
- 正在查找合适地点。
- 正在计算路线和时间。
- 正在检查冲突。

不得暴露冗长模型思维过程。生成时间较长时，应允许用户离开当前页面并在完成后返回结果。

### 11.3 行程详情页

- 默认显示第一天的时间轴和地图。
- 天数使用标签页或分段控件切换。
- 地图与时间轴中的地点选中状态保持同步。
- 主要编辑操作直接作用于行程项。
- 自然语言修改入口常驻但不遮挡主要内容。
- 冲突和待核验信息应就近显示。

### 11.4 变更确认

重新规划完成后展示：

- 删除了什么。
- 新增了什么。
- 哪些项目被移动。
- 总预算、交通时间和强度如何变化。
- 应用修改、继续调整、保留原方案三个操作。

## 12. 非功能需求

### 12.1 性能

- 首个可用方案目标在 60 秒内返回。
- 用户编辑后的局部校验目标在 3 秒内完成。
- 普通局部重排目标在 20 秒内返回。
- 工具调用应支持超时、重试、缓存和熔断。

### 12.2 稳定性

- 单个外部工具失败不应导致用户行程数据丢失。
- 生成过程应支持幂等处理，避免重复创建多个相同行程。
- 每次正式修改前应创建可恢复版本。

### 12.3 安全与隐私

- 仅收集完成规划所需的个人信息。
- 精确住宿位置和实时位置属于敏感数据，应明确用途并限制访问。
- 日志中避免记录不必要的个人身份信息和完整位置轨迹。
- 分享链接默认不公开，支持失效和撤销。
- 外部工具结果必须进行输入清洗，防范提示注入和异常字段。

### 12.4 可观测性

系统应记录但不限于：

- 各阶段耗时。
- 工具调用成功率和超时率。
- POI 无结果率与同名消歧率。
- 生成后的校验失败类型。
- 用户修改和重新规划次数。
- 行程最终保存及实际使用情况。

### 12.5 可扩展性

- 地图、天气、内容和票务服务使用统一工具适配层。
- 领域模型不与单一地图服务字段强绑定。
- 调度器支持未来增加多城市、跨日交通和实时事件约束。

## 13. 核心指标

### 13.1 北极星指标

**有效行程完成率**：创建行程的用户中，成功生成并至少保存、锁定或修改过一个行程项的用户比例。

### 13.2 漏斗指标

- 创建页访问到开始输入的转化率。
- 开始输入到提交生成的转化率。
- 提交生成到成功返回方案的比例。
- 返回方案到保存行程的比例。
- 保存后再次打开行程的比例。

### 13.3 质量指标

- 地点有效率。
- 路线计算覆盖率。
- 硬约束冲突率。
- 营业时间及关键信息核验覆盖率。
- 用户删除或替换的行程项比例。
- 首次方案直接采用率。
- 平均局部重排次数。
- 用户报告错误率。

### 13.4 性能与成本指标

- 首次生成 P50、P90 耗时。
- 单次行程平均模型调用成本。
- 单次行程平均地图工具调用次数。
- 工具缓存命中率。
- 外部服务错误率。

## 14. 测试与评估方案

### 14.1 离线评估集

建立覆盖不同城市和约束的标准测试集，至少包含：

- 不同旅行天数和预算。
- 儿童、老人及无障碍场景。
- 固定预约和多个必去地点。
- 较晚抵达、较早离开场景。
- 预算不足或约束相互冲突场景。
- 同名地点、跨行政区和周边景点场景。
- 雨天替换和临时迟到场景。

### 14.2 自动评估

- JSON Schema 合法性。
- 日期、时间顺序和重叠检查。
- 地点城市归属检查。
- 路线时间覆盖检查。
- 硬约束满足率。
- 预算计算一致性。
- 局部修改范围稳定性。

### 14.3 人工评估

由熟悉目的地的评测人员按 1–5 分评价：

- 地点选择质量。
- 路线合理性。
- 时间可执行性。
- 行程节奏。
- 个性化程度。
- 解释清晰度。

### 14.4 MVP 建议发布门槛

- 正式行程 JSON 结构合法率 ≥ 99%。
- 明显时间重叠率 ≤ 1%。
- 正式行程地点可定位率 ≥ 98%。
- 相邻地点交通信息覆盖率 ≥ 95%。
- 锁定项目在局部重排中的意外变更率为 0。
- 标准评估集中的硬约束满足率 ≥ 95%。

## 15. 风险与应对

| 风险 | 影响 | 应对方案 |
|---|---|---|
| 地图或第三方数据过期 | 行程不可执行 | 显示来源与获取时间，对关键信息增加出发前确认提示 |
| 模型虚构地点或详情 | 损害信任 | 未经工具核验的地点不得进入正式行程 |
| 工具调用成本过高 | 商业模型不可持续 | 缓存、批量查询、候选集限制、调用预算控制 |
| 规划时间过长 | 用户流失 | 阶段反馈、异步生成、先返回骨架再补充详情 |
| 行程算法过度追求覆盖 | 体验疲劳 | 设置节奏模型、缓冲时间和每日强度上限 |
| 营业时间与预约信息缺失 | 到达后无法游览 | 状态标识、关键项二次核验、提供替代地点 |
| 局部修改引发连锁变化 | 用户失去控制 | 锁定机制、影响范围计算、变更确认和版本撤销 |
| 用户位置与住宿数据泄露 | 隐私风险 | 最小化收集、访问控制、脱敏日志、分享链接可撤销 |
| 外部内容提示注入 | 智能体行为异常 | 工具数据与指令隔离、字段白名单、输出校验 |

## 16. 迭代路线图

### 阶段 0：技术验证

- 打通地图 MCP 的地点搜索、详情和路线能力。
- 建立统一 POI 与路线数据模型。
- 完成单日 3–5 个地点的路线排序和时间校验。
- 建立最小离线评估集。

### 阶段 1：MVP

- 单城市 2–5 日旅行需求收集。
- 按天时间轴和地图展示。
- 路线、预算和基础约束校验。
- 删除、替换、锁定和单日重排。
- 行程保存和版本恢复。

### 阶段 2：体验增强

- 多方案对比。
- 天气联动与旅行中实时调整。
- 分享、日历和图片导出。
- 酒店区域反向推荐。
- 更完整的营业时间和预约信息核验。

### 阶段 3：交易与协作

- 酒店、门票、活动和交通预订入口。
- 多人协作、投票和偏好融合。
- 旅行提醒、导航和订单管理。
- 会员功能及商业化实验。

### 阶段 4：复杂旅行

- 多城市和跨城交通。
- 国际旅行、时区及入境要求。
- 基于历史偏好的长期个性化推荐。

## 17. MVP 验收场景

### 场景一：从零生成

用户输入：“10 月 1 日到 4 日去成都，两个人，总预算 4000 元，喜欢美食和历史，不想太累。”

验收结果：

- 系统正确识别城市、日期、人数、预算、兴趣和节奏。
- 必要时询问抵达、离开时间及住宿位置。
- 返回逐日时间轴、地图路线、交通方式和费用估算。
- 不出现明显跨区折返和时间冲突。

### 场景二：保留固定安排

用户补充：“第二天上午 10 点的博物馆已经预约，不能移动。”

验收结果：

- 该项目被标记为已预约或锁定。
- 后续重新规划不移动或删除该项目。
- 系统围绕固定时间安排前后交通和其他活动。

### 场景三：局部重排

用户提出：“第三天下午可能下雨，换成室内活动，晚餐保持不变。”

验收结果：

- 只修改第三天下午相关项目。
- 晚餐时间和地点保持不变。
- 新地点位于合理路线范围内。
- 展示修改前后费用和交通时间变化。

### 场景四：无法满足全部条件

用户要求在半天内访问多个距离较远的必去地点。

验收结果：

- 系统识别约束冲突。
- 不生成明显不可执行的时间表。
- 向用户说明原因并提供减少地点、延长时间或提高交通成本等选项。

---

## 18. 待确认事项

在进入交互设计和技术方案前，需要进一步确认：

1. 首发平台为响应式 Web、小程序还是原生应用。
2. 首发城市范围及是否限制为高德数据覆盖区域。
3. 是否在 MVP 纳入酒店费用，还是仅记录用户已订住宿。
4. 是否接入天气、内容评价、门票或营业时间数据源。
5. 规划结果是否允许未登录体验，以及何时要求登录。
6. 地图 MCP 的授权方式、调用额度、延迟和商用限制。
7. 是否支持用户实时位置，以及相应隐私授权流程。
8. MVP 的目标用户规模、单次规划成本上限和预期响应时间。

---

## 19. 结论

MVP 应聚焦“真实、合理、可执行、可修改”四个关键词。产品竞争力不只来自大模型生成文本，也来自结构化需求模型、地图数据核验、约束调度、局部重排和版本控制共同形成的完整规划闭环。

首版应优先把单城市短途自由行做深，并通过地点有效率、硬约束满足率、首次方案采用率和局部重排稳定性验证产品价值，再逐步扩展天气联动、多人协作、预订交易和多城市旅行。
